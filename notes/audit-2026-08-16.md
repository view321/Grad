# Audit — Grad, 2026-08-16

Scope: the whole system as it stands on `dev` at `91ad96f` plus the uncommitted
working tree. ~53k lines of Python across 128 files, 46 test modules. Read the
code, the two handoffs, the README, and — the part that turned out to matter
most — **the live workspace on this machine**, because what the ledger actually
contains is a different claim from what the code can do.

---

## 1. Verdict in one paragraph

The machinery is exceptional and it has barely been driven. Every mechanism the
design promises exists, is tested against real files rather than mocks, and is
documented with the reasoning intact — this is some of the most disciplined
research-infrastructure code I have read. But the live ledger holds **four runs,
all of them `--smoke`, none of them bound to a prediction, and zero collected
results**. The corpus has **zero papers**. The eval set has **three rows, all
marked `seed: true`**. So the five submit gates, the deviation arithmetic, the
verdict loop and all four report rules have never once run against a real
result. The risk here is not that the system is wrong; it is that it is
*unfalsified*. The next unit of work is not another subsystem — it is one
complete cycle through the one that exists.

Every run in `runs.jsonl` took the `--smoke` carve-out, which is *gate-exempt by
design*. So `expectation_id` is `null` on all four, `results` is `{}` on all
four, and `deviations` is `[]` on all four. The centrepiece of the architecture
— preflight → prediction → spend → staleness → concurrency, then collect,
deviate, judge, report — has never run end to end outside `pytest`.

`exp-20260816T045844-0f315c` is still open and still unbound. Its blocker (the
phantom in-flight run) was cleared six hours later. Nothing has been submitted
against it since.

## 3. Strengths

**1. The central rule is real, not aspirational.** "Anything that spends money,
destroys work, or must be true before the fact is enforced mechanically" is
implemented as programs that refuse. `check_preflight` treats `{}`, `{"ok":
null}` and a bare string as *not a pass* rather than enumerating known-bad
states. `check_smoke_caps` refuses a target whose hourly rate it cannot look up,
because a cap it cannot compute is not a cap. `_finite()` rejects `nan`/`inf`
because NaN fails every comparison and would have silently disabled the cost
cap. This is what defensive design looks like when someone has actually thought
about the adversary being their own future self under deadline.

**2. Concurrency correctness is taken seriously in the right place.** The
in-lock re-check in `ledger_store.append_run_event` — binding first, then the
caller's spend precondition, matching `check_submit`'s order so the refusal is
the same inside the lock as outside it — is the kind of thing most projects get
wrong and never find out about.

**3. The pure cores are genuinely pure and genuinely tested.** `core/evolution.py`
is a complete evolutionary search policy with no I/O, no clock and an injected
`Random`. `bandit_select`'s `pending` parameter — counting in-batch pulls as
pulls with no reward, so a generation planned in one pass does not pick the same
arm four times — is a subtle bug that most implementations ship with. `ui/models.py`
is 61 pure functions turning ledgers into plain data, so the windows are testable
without a browser.

**4. Failures are recorded rather than smoothed over.** The README documents the
ceiling that could only see 1.2% of the tokens, with the measured numbers.
`notes/kaggle-backend-check.md` documents a bug the author caused, the queue
cycle it cost, and the fix, then proposes two upstream fixes in preference
order — and the system shipped the second one. `_apply_verdict` marks a verdict
for an unreported quantity as `orphan: true` rather than dropping it.

**5. Tri-state honesty throughout.** `in_range` is `True`/`False`/`None`, where
`None` means "no program can settle this" — relational predictions, non-numeric
results, missing quantities. The SQLite index stores NULL to preserve the
distinction. `unjudged_deviations` filters on `is not True`, so the *preferred*
prediction type doesn't silently fall out of the pending list.

**6. The error surface is a design artefact.** Fifteen exit codes where 6, 12,
13 and 14 are deliberately distinct because they have different fixes, and every
refusal carries a `fix` field that is usually the literal next command.

## 4. Weaknesses, ranked, with fixes

### W1 — No statistical layer at all. *(biggest scientific gap)*

> **Resolved after this note was written.** Everything under **Fix** below is
> implemented: `parse_samples` / `read_metrics` collect every value a run reports
> per quantity, `core/stats.py` summarises and compares interval-to-interval with
> the tri-state `in_range`, `compute_deviations` records `n`, and `report check`
> has the fifth rule (`check_replication`). The diagnosis below is kept as the
> pre-PR snapshot it was, because the argument for the shape is still the reason
> the code has that shape.

An expectation binds **one quantity** to one interval; `compute_deviations`
compares **one run's single number** to it. There is no seed in `spec.toml`, no
notion of repeats, no variance, no confidence interval, no multiple-comparison
awareness anywhere in the ledger or the report gate. A run that reports
`val_loss = 3.05` against a predicted `[2.9, 3.2]` is recorded as in-range with
the same confidence whether the run-to-run spread is 0.001 or 0.3.

For a system whose stated purpose is "a surprise is an alarm", this is the one
place where the alarm cannot be calibrated. It also interacts badly with
`tools/evolve.py`: an evolutionary search selects on `combined_score`, and
selecting on a noisy single-sample metric is how you evolve a lucky seed.

**Fix.** Additive, in the shape the ledger already uses:
- `[execution] seed` and `[execution] repeats` in the spec, both in the
  submission hash (unlike `max_concurrent`, these *do* change the numbers).
- `collect` records `results` as before plus `results_by_seed` when repeats > 1.
- `compute_deviations` gains `n`, `mean`, `sd`, and compares the **interval to
  the interval** rather than a point to an interval; `in_range` becomes `None`
  ("overlapping, needs a verdict") when the intervals overlap but neither
  contains the other. That is exactly the tri-state this codebase already
  believes in.
- `report check` gains a fifth rule: a `\gradnum` whose run has `n = 1` is a
  finding, answerable ("single seed, stated as such in §4") but not silent.

### W2 — Pre-registration covers one quantity; the report will publish the rest

`report.quantity_value` resolves **any** key present in `run.results`, and
`unjudged_for` only inspects deviations — which exist only for the single bound
expectation's quantity. So a run that emits `loss`, `accuracy` and `throughput`
can pre-register `loss` and publish `accuracy` with no prediction, no deviation,
and nothing to judge. The README's row "A prediction exists before the result
does" is true of one number per run.

**Fix.** Two options, both cheap:
- Allow `--expect` to be repeated, bind a list, and compute deviations per
  bound expectation; or
- (smaller) have `check_claims` emit a finding — not a refusal — when a cited
  `(run_id, quantity)` has no expectation bound to it: *"this number was not
  pre-registered."* That preserves exploratory reporting while making the
  distinction visible, which is the whole point of the ledger.

### W3 — The background supervisor swallows its own death

`cmd_start` spawns the supervisor with `stdout=DEVNULL, stderr=DEVNULL`. If the
supervisor dies before reaching its own `try` — an import failure, a bad config,
a `_claim` timeout — **nothing is written anywhere**: the log file was
pre-created empty, no exit event is recorded, and the task folds to `lost`.

This is not hypothetical; I hit it. Three `test_tasks.py` tests failed under one
of the two Python environments on this machine, and the only way to find the
cause was to run `python -m tools.task --help` by hand. From the app you would
see a task that started and vanished, with no diagnostic on any surface.

**Fix.** Point the supervisor's `stderr` at the task's own log file — it already
exists and `task output` already reads it. Two lines:

```python
supervisor_log = open(tasklib.log_path(task_id), "a", encoding="utf-8")
subprocess.Popen([...], stdout=subprocess.DEVNULL, stderr=supervisor_log, ...)
```

Also record a terminal event on the `_claim` timeout path, so "no start record
appeared" is distinguishable from "vanished".

### W4 — `sqlite-vec` is loaded, advertised, and never used

`corpus._load_vec()` loads the extension and sets `_VEC_AVAILABLE`;
`corpus.stats()` reports `"sqlite_vec": has_vec()`. But no `vec0` virtual table
is ever created and no `vec_distance_*` function is ever called — `store_vectors`
writes to the fallback `chunk_vectors` BLOB table and `vector_search` does a
**full table scan with cosine similarity in a Python loop**. The stats output
implies an ANN index that does not exist.

Fine at 20 chunks; the module's own comment says revisit past ~100k, and a few
hundred ingested papers will get there.

**Fix.** Cheapest honest version: rename the stat to `"sqlite_vec_loaded"` and
add `"vector_search": "brute_force"`. Better: actually use it — a `vec0` table
keyed on `chunk_id` and a `MATCH`-based nearest-neighbour query, with the
existing brute-force path kept for when the extension is absent.

### W5 — The one live project has no ceilings, so every budget gate is inert

`minimamba` was created with `budget: {}`. All three ceilings read `null`:

```
gpu_usd      ceiling null   spent 0.0
quota_tokens ceiling null   spent 1,128,678
credits_usd  ceiling null   spent 0.004445
```

Consequently `check_project_spend` always passes, `check_turn_budget` always
returns `None`, and `hooks._cost_bearing_over_budget` never denies. The README
devotes more words to the token ceiling than to any other mechanism, and in the
only project that exists it is switched off — not by a bug, but because
`budget new` permits an unbounded project silently.

**Fix.** Make `budget new` require at least one ceiling or an explicit
`--unbounded` flag, and have `budget status` and the UI meter say *"no ceiling
set — nothing is bounding this project"* rather than rendering a blank gauge.
The failure mode this project cares about is a ceiling that stops existing
without anyone noticing; that is the current state.

### W6 — The quota-consuming funnel stages are unmeasured *and* dominant

Now that the instrument exists, it has an answer, and §5's open question is
answerable for the first time:

| stage | calls | weighted tokens | per call | % of all quota |
|---|---:|---:|---:|---:|
| `main` | 8 | 797,650 | 99,706 | 70.7% |
| `funnel.triage` | 4 | 189,662 | **47,415** | 16.8% |
| `funnel.expand` | 10 | 141,365 | 14,136 | 12.5% |
| `funnel.rerank` | 4 | 0 (credits: $0.0044) | — | 0.0% |

**Triage costs roughly half a full conversation turn, every time, to cut 50
candidates to 15.** The stage that costs actual money is a rounding error beside
it. And two of the four traces I read ran with `--no-triage`, which suggests the
cost is already being felt and worked around by hand.

Whether that 47k is worth paying is precisely what `evals/retrieval.jsonl` was
supposed to decide, and it holds three rows, all `"seed": true`.

**Fix.** This is next-step material, not a code change — see §5 item 3.

### W7 — Two Python environments, one of them stale and broken

`C:\Python314`'s user-site editable install dates from Aug 15 and its
`MAPPING` contains only `core`, `tools`, `ui` — no `agent`, no `hooks`. Under
that interpreter, `grad --version` from any directory other than the checkout
fails with `ModuleNotFoundError: No module named 'agent'`, and three
`test_tasks.py` tests fail. Under `D:\GradientAgent\.venv` the mapping is
complete and everything passes.

The code is correct — `py-modules = ["agent", "hooks"]` is in the right table.
The install is stale. But a project with a self-updating installer and a
documented `grad` entry point should not be able to be in this state silently.

**Fix.** Have `agent.py --check` report `sys.executable`, the resolved
`grad` script path, and whether `import agent` succeeds from a directory other
than the install root. That is three lines and it turns a mystifying failure
into a sentence.

### W8 — `tools/task.py` depends on a top-level module across the package boundary

`import hooks` in `tools/task.py` is the only cross-boundary import of a
top-level module in the codebase, and it is what makes W7 bite the task runner
specifically. The docstring says `evaluate_bash` is pure "for exactly this
reason" — so the pure part wants to live where the pure parts live.

**Fix.** Move `evaluate_bash`, `Denial`, `cost_bearing_command` and the patterns
into `core/deny.py`; leave `hooks.py` as the thin SDK adapter that imports them.
`core` is a real package everywhere, so the dependency stops being fragile.

### W9 — `core/http.py` is four vendors in one 1,436-line module

Semantic Scholar, Papers with Code, Asta (with a hand-rolled MCP-over-SSE
client), Context7, plus rerank on two rails, plus embeddings. It is the second
largest file and the one most exposed to third-party churn — every lesson in the
README's "what a live run found" section landed here.

**Fix.** Split to `core/clients/{s2,pwc,asta,context7}.py` with the shared
`_httpx`, cache, throttle and normalisation helpers staying in `core/http.py`.
Mechanical, and it makes "Asta changed its envelope again" a one-file diff.

### W10 — The reranker is on a free tier that cannot serve the requests it makes

A live trace: `rerank unavailable: rerank returned 429: "You have not yet added
your payment method ... reduced rate limits of 3 RPM and 10K TPM"`. The
successful calls sent 17,528–29,583 tokens each. Stage 2 is therefore expected
to fail on any pool above ~40 documents, and it degrades to `pool[:rerank_top]`
— an *unranked* prefix — with a warning in the trace that nothing surfaces to
the agent's turn.

**Fix.** Either add a payment method, or batch the rerank under the TPM limit
and merge, or lower `[retrieval] candidates`. Regardless: promote the fallback
from a trace warning to the tool's `note` field, because "reranked" and
"the first 50 by RRF" are different results and the caller currently cannot
tell.

### W11 — The provenance rule is currently self-violating

All four run records carry `code_version.dirty: true`, and
`report.check_code_versions` raises a finding for exactly that. The working tree
has 35 modified and 15 untracked files, including four new `core/` modules and
two new `tools/` CLIs. **No report citing any existing run could pass its own
gate today.**

**Fix.** Commit the tree. `core/evolution.py`, `core/mutate.py`, `core/tasks.py`,
`core/kaggle_quota.py`, `tools/kaggle.py`, `tools/task.py` and six test modules
are substantial finished work sitting untracked.

## 5. What to build next, in order

**1. Close the loop once, for real. (highest value by a wide margin)**

Everything is in place: the expectation is open and unbound, the phantom run is
abandoned, the smoke passes on real hardware, and Kaggle costs $0.

```bash
python -m tools.kaggle submit --spec pipelines/kaggle-smoke/spec.toml \
  --expect exp-20260816T045844-0f315c --json
python -m tools.kaggle collect <run_id> --json
python -m tools.ledger verdict <run_id> --quantity cuda --verdict real --note "..." --json
python -m tools.report draft --project minimamba --json
python -m tools.report check --project minimamba --json
```

That single sequence is the first live exercise of all five gates, the
deviation arithmetic, the verdict loop, and all four report rules. It costs
nothing and it will find things — every previous live contact with this system
has. Do it before writing any new subsystem.

**2. Give the corpus something to be.** Zero documents ingested means tier 2 —
"where did I see that lemma", the half no external index can answer — does not
exist yet, `_local_ranked` contributes nothing to the RRF fusion, HyDE has
nothing to embed against, and `paper_ingest` (the least-covered tool in the
suite) is unproven. Ingest the 15 survivors from the Mamba searches already
sitting in `notes/funnel/`.

**3. Harvest and grade the eval set.** §12 step 9's prerequisite — a week of
real use — has now happened: 5 sessions, 8 funnel traces, ~10 real questions.
`tools.traces harvest` exists to do exactly this and produces rows ungraded on
purpose. Grade 20–30, then answer W6 with numbers: does triage's 47k tokens per
search buy anything a $0.001 rerank does not. This is the one decision the whole
quota-instrumentation effort was built to enable, and it is now the only one
still blocked on effort rather than on data.

**4. The statistical layer (W1).** Seeds, repeats, and interval-vs-interval
deviations. This is the largest genuinely *new* design work, and it should land
after step 1 so it is designed against a real run record rather than an
imagined one.

**5. Then, and only then, phase 2 of the campaign loop.** `--remote` is
correctly still refused. The reasoning in the README — don't do the ledger work
and the spend work simultaneously against live GPU jobs — is right, and step 1
is the thing that discharges it.

**Deliberately not next:** anything in the UI, any new backend, any new tool.
The tool surface is already wider than the evidence supporting it.
